## R1 — Which module owns the feature

**Decision**: `cms`. The two settings join the existing `cms_page_builder` group; the endpoints,
permission, error codes, audit command, i18n keys and docs are `cms`' own.

**Rationale**: the product owner placed the configuration "in the Page Builder section of
Settings", which *is* `cms`' `cms_page_builder` group; the action lives in `cms`' editor; the
knowledge of what a Page Builder document is (blocks, slots, the registry of declarations) is
`cms`'. Constitution I: the feature extends the module that owns its domain.

**Alternatives rejected**:
- *A new module (`content_translation`)* — would own no data and no domain noun; its settings would
  sit in its own group, not the Page Builder's, contradicting the request; it would need a
  cross-module contribution into `cms`' editor and a read of `cms`' registry.
- *`prompt_actions`* — it is the command-palette assistant. Its activation and its own kill switch
  (`prompt_actions.enabled`, default `false`) would then govern page translation, which an operator
  cannot be expected to guess.

## R2 — How the backend talks to the model provider

**Decision**: extract `prompt_actions`' provider-neutral LLM transport — `provider.ts` and the three
adapters — into a **new stateless library package `@endora-commerce/llm-client`**
(`packages/llm-client/`), make `prompt_actions` import it (behaviour-preserving move, its adapter
tests move with the code), and have `cms` use it for translation. Each consumer keeps resolving its
own credential reference through the `credentialsService` port, exactly as today.

**Rationale**:
- Two modules now need the same three provider protocols. A library is the only shape that shares
  code without creating a module edge: it has no lifecycle, no settings, no state and no activation,
  so neither consumer's off-state is affected by the other (Constitution I, XVII).
- It reuses code that is already in production and tested; **no third-party runtime dependency** is
  added (Constitution IV). Its only dependency is `zod`, already in the stack.
- It keeps the `credentials` module's charter intact ("never interprets provider meaning",
  `credentials/src/manifest.ts`).
- Precedent for a stateless shared library consumed by modules: `@endora-commerce/page-builder-core`.

**Alternatives rejected**:
- *Copy the adapters into `cms`* — two copies of three HTTP protocols that will drift (the
  `baseUrl` gap would be fixed in one and not the other).
- *`prompt_actions` publishes a completion port* — couples page translation to the assistant's
  activation; a module would depend on another for something that is not that module's domain.
- *`credentials` publishes an `llmCompletion` port* — attractive because secrets would never leave
  `credentials`, but it turns the store into a gateway making outbound calls to provider APIs and
  contradicts its recorded charter (feature 058). Recorded as a possible later evolution, not done
  here.
- *A new `@endora-commerce/platform` barrel* — the platform publishes five barrels a module may name
  (`check:platform-surface`); an LLM client is not host infrastructure.
- *A provider SDK (`openai`, `@anthropic-ai/sdk`, Vercel `ai`)* — three new runtime dependencies for
  what 400 lines of tested fetch code already do.

**Cost accepted**: a new workspace package carries a `package.json` with an `exports` map,
`tsconfig.json` + `tsconfig.build.json`, a `tsconfig.base.json` `paths` entry, a `LICENSE`, a
generated `README`, a changeset (it joins the lockstep `fixed` group through its
`@endora-commerce/*` name, `.changeset/config.json`), and the dependency entry that
`manifests:generate` renders into `mod-cms` and `mod-prompt-actions`. Whether an instance scaffolded
by `packages/cli` resolves it must be proven by the CLI's own tests (tasks T008, T057).

## R3 — How the model is made to return structured output

**Decision**: one **forced tool call**. The request declares a single tool
`cms.submit_translations` whose input schema is `{ translations: [{ id: string, text: string }] }`,
and `@endora-commerce/llm-client` gains an optional `toolChoice: { name }` on `LlmRequest`, mapped to
each provider's native "force this tool" option (Anthropic `tool_choice: {type:'tool'}`, OpenAI
`tool_choice: {type:'function'}`, Google `toolConfig.functionCallingConfig {mode:'ANY',
allowedFunctionNames}`). The answer is the first tool call's `arguments`, validated with Zod.

**Rationale**: the adapters already speak tool calling and already validate responses at the
boundary; all three providers support forcing a tool; a JSON-schema-shaped answer is far more
reliable than parsing free text. `toolChoice` is additive and absent by default, so the assistant's
requests are byte-identical.

**Alternatives rejected**: provider "JSON mode" (three different switches, Anthropic has none);
free-text answer with delimiters (fragile, no schema).

## R4 — What on a canvas is translatable

**Decision**: a **per-block declaration** made by the block's owning module:
`BlockDefinition.translatable?: Array<{ path: string; format?: 'plain' | 'tiptap' }>` in
`packages/contracts/src/cms.ts`, carried into the descriptor's component entries (additive,
optional). `cms` declares it for each of its CMS-context blocks; `catalog` for its CMS-context blocks
that carry text. A first-party CMS-context block **must** declare it (an empty array is a valid
declaration meaning "nothing to translate"), enforced by a unit test over the manifests; a block with
no declaration (third-party, overlay) is reported as *not translatable* and left untouched (FR-025).

**Rationale**: the decision whether a string is prose or a URL/code is semantic and only the block's
owner knows it (Constitution I, XIV — entity-agnostic: `cms` does not hard-code other modules'
blocks). It fails safe: a new or unknown block is never sent.

**Alternatives rejected**:
- *Heuristic on field type* (`text`/`textarea`/`richtext`) — `cms.Button.href`, `cms.RawJs.script`,
  `cms.RawHtml.html` and `catalog.ProductCard.productSlug` are all `text`/`textarea`; and the declared
  `fields` are incomplete (`cms.Accordion` declares none), so it would both translate code and miss
  prose.
- *Send whole `props` objects and let the model decide* — sends URLs, colours and ids to a third
  party, costs several times the tokens, and invites structural drift that must then be undone.
- *Derive from the admin-side Puck field configuration* — the backend cannot read it, and rich text
  is a `type: 'custom'` field with no semantics.

## R5 — The path grammar

**Decision**: `segment ( '.' segment )*`, where a segment is a prop name
`[a-zA-Z][a-zA-Z0-9_]*` optionally followed by `[]` meaning "every element of this array". Examples:
`heading`, `items[].title`, `items[].content`, `headers[].label`. Validated by a regex in the
contract (`translatablePathRe`) and by `defineModuleManifest` at declaration time. A path resolves to
zero or more **string** leaves; a non-string value at a path is ignored (not an error), so an
optional prop that is absent costs nothing. `format: 'tiptap'` marks a path whose value is a TipTap
JSON document (R6). Slots (`content: Slot`, `slides: Slot`) are **not** declared: the walker
descends into every child component generically, and each child is handled by its own declaration.

**Rationale**: covers every shape in `component-types.ts` without a general JSONPath engine
(Constitution IV). Responsive values are never text, so no responsive syntax is needed.

**Alternatives rejected**: JSONPath/JSON Pointer libraries (dependency, more power than needed);
per-block extractor functions (code instead of data — cannot travel on the descriptor and cannot be
read by a static check).

## R6 — Rich text

**Decision**: a TipTap document is translated **one block-level node at a time** (paragraph, heading,
list item paragraph, blockquote paragraph, table cell paragraph). Each such node becomes one segment
whose inline content is encoded as text with **numbered inline tags** for marked runs —
`Kup <0>teraz</0> i <1>oszczędź</1>` — where the tag table (`0 → [bold]`, `1 → [link href=…]`) stays
on the server and is **never** sent. The model must return the same set of tags; the decoder rebuilds
text nodes with the original marks. Hard breaks become `<br/>` and are restored. A segment whose
tags do not round-trip keeps its original wording and is counted as untranslated (FR-020).

The derived `html` props are **not** produced on the server. The admin, before applying a result,
runs Puck's `resolveAllData(data, config)` with the editor's own config (`@puckeditor/core` 0.23
exports it; the invoice tests already use it, `admin/test/modules/invoices/described-invoice-blocks.test.tsx`),
which re-runs each block's `resolveData` and so `coerceRichContentProps` regenerates `html` from the
translated TipTap content. `coerceRichContentProps` also prefers the generated HTML at render time,
so a stale stored `html` could not be shown even if this step were skipped; the step is there so the
**stored** document is consistent.

**Rationale**: translating text nodes one by one breaks sentences at every bold word and produces
ungrammatical output; translating whole HTML risks markup damage and sends link targets. Inline tags
are the standard approach of CAT tools (XLIFF inline codes) and keep link targets on the server.

**Alternatives rejected**: send HTML and parse it back (the backend would need a TipTap/HTML parser,
link targets leave the platform, sanitiser interplay); generate HTML on the server (pulls
`@tiptap/core` into `cms`' backend for a value the editor already regenerates).

## R7 — Placeholders and things that must survive

**Decision**: the system prompt instructs the model to keep `{{…}}` placeholders, inline tags, URLs,
e-mail addresses and numbers verbatim; the decoder **verifies** that the multiset of `{{…}}` tokens
and the inline tag set of every returned segment equal the source's, and rejects the segment
otherwise (keeps the original, counts it untranslated).

**Rationale**: instructions alone are not a guarantee; verification makes FR-017 testable without a
real model.

## R8 — Segmentation, batching, limits

**Decision** (constants in `packages/modules/cms/src/backend/services/translation/limits.ts`, not
settings):

| Constant | Value | Why |
| --- | --- | --- |
| `MAX_SOURCE_CHARACTERS` | 40 000 | one long landing page; above it the request is refused before anything is sent (`413`, FR-023) |
| `MAX_CHUNK_CHARACTERS` | 6 000 | keeps one answer well inside every supported model's output budget |
| `MAX_CHUNK_SEGMENTS` | 150 | bounds the JSON the model must echo ids for |
| `CHUNK_CONCURRENCY` | 2 | bounds provider rate-limit pressure per click |
| `CALL_TIMEOUT_MS` | 60 000 | per provider call, via `AbortSignal.timeout` passed to `fetch` |
| `MAX_OUTPUT_TOKENS` | 8 192 | per call; a `max_tokens` stop splits the chunk in two and retries each half once |

Identical source strings are translated once (deduplicated before chunking). Segment ids are
opaque (`s1`, `s2`, …) and are the only link between request and answer.

**Rationale**: SC-004 (95% under 30 s for ~5 000 characters → one chunk, one call) and a hard upper
bound on a single click's cost and duration (≤ 7 chunks, ≤ 4 sequential rounds, each ≤ 60 s).

**Alternatives rejected**: an operator setting for the limit (YAGNI; the owner may ask for it —
*Decisions for the owner* 7); one call for everything (output token limits).

## R9 — Synchronous request, not a queue job

**Decision**: `POST /api/v1/admin/cms/page-builder/translate` performs the translation in the request
and returns the result. The admin aborts the `fetch` on cancel; the server finishes its current calls
and discards nothing it has not yet sent.

**Rationale**: the work is interactive (an editor waits with the canvas open), bounded (R8), produces
no stored state and is not repeatable work. Principle X governs **queue-backed** operations; none is
introduced.

**Alternatives rejected**: a BullMQ job with polling — would need the unsaved canvas persisted
server-side, a status endpoint and a polling UI for a ≤ 1-minute operation; streaming progress over
SSE — YAGNI.

## R10 — How the result is applied

**Decision**: client-side, through the editor's existing `applyCanvasData` (the same path as Copy
from language and Apply template): the translated tree, after `resolveAllData`, replaces the active
tab's canvas as an **unsaved** change. The editor keeps an in-memory snapshot of the canvas from
before the click and offers **Restore previous content** until the next save, translation or tab
change.

**Rationale**: zero new persistence, zero new write path; the existing save, version check
(`If-Match`/`version`) and Command Bus auditing of content writes apply unchanged.

**Alternatives rejected**: the server writes the translation into the stored language (a write the
editor did not ask for, conflicts with unsaved edits); a per-block accept/reject review screen
(substantial UI; out of scope, spec *Out of scope*).

## R11 — Settings, capability and the `credentials` edge

**Decision**:
- Two settings in `cms`' manifest, group `cms_page_builder`, platform-wide:
  `cms.page_builder.translation.enabled` (`boolean`, default `false`) and
  `cms.page_builder.translation.llm_credentials` (`credential_ref`, `configurationType: 'llm'`,
  default `''`). Rows are created by the existing manifest reconciler; **no migration**.
- Read per request through `settingsReadPort.get(code, null, schema)` (platform-wide read, D-41
  spelling already used in `cms/src/backend/index.ts`). The settings module's cache and its
  invalidation on write are reused; **no new cache** and no new pub/sub channel (FR-004).
- The credential is resolved through `lazyPort<CredentialsPort>(ctx, 'credentialsService')` **per
  call**, after `effectiveState.isPresent('credentials')`; absent ⇒ capability `unavailable`.
  Declared in `cms`' manifest as `nonBindingDependencies: [{ moduleId: 'credentials', name:
  'credentialsService', kind: 'degrades-without', whenAbsent: 'Page Builder translation is
  unavailable; every other CMS function keeps working.', reason: … }]`.
- `GET /api/v1/admin/cms/page-builder/translation` answers the capability:
  `ready | disabled | not_configured | unavailable`, plus `provider`, `model` (non-secret) and
  `maxCharacters` when ready.

**Rationale**: mirrors `prompt_actions`' capability shape, which the palette already proves; the
editor can show the disabled state **before** a click (FR-005). `degrades-without` is the honest
classification: the capability endpoint degrades to `unavailable` rather than propagating a 503.

**Alternatives rejected**:
- *`credentials` in `dependencies`* — `cms` could not run without `credentials`, and `credentials`'
  activation control would refuse while `cms` is on, for a function that is optional and off by
  default.
- *`refuses-without`* — would answer 503 on the capability probe, so the editor could not tell
  "unavailable" from "CMS is off".
- *Embed the capability in `GET …/page-builder/config`* — that descriptor is read under `cms.read`
  by every Page Builder user and describes blocks; the capability is per-permission.

## R12 — Permission

**Decision**: a new code **`cms.translate`** ("Translate Page Builder content with AI"), gating both
endpoints; labels in `cms`' own bundle (`adminRoles.permission.cms.translate`, en + pl). No
`requires` entry: the save permission differs by host (`cms.write` for CMS content, the blog's own
code for blog posts), and `requires` is advisory anyway.

**Rationale**: sending content to a third party and spending money is a separate decision from
editing content; it is the same reasoning that gives the assistant `prompt_actions:use`.

**Alternatives rejected**: reuse `cms.write` — every CMS editor could spend model budget and egress
content; blog-only editors could not translate at all.

## R13 — Auditing

**Decision**: an **audit-only Command** `TranslatePageBuilderContentCommand` (action
`cms.page_builder.translate`) run through `CommandBus.run` **after** the provider calls finish, once
per request in which at least one chunk was sent. Its `after` state is metadata only: target
language, source language or `null` (detected), resource `{ type, id }` when the client named one,
provider, model, segment count, character count, outcome (`completed | partial | failed`), and counts
of translated / untranslated segments. `objectType` is the resource type or `page_builder_canvas`;
`objectId` the resource id or `null`. Not reversible.

**Rationale**: `cms` is a Command-Bus-migrated module (its cradle carries `commandBus`), so
Principle XIII forbids a hand-written `AuditPort.record` here; the translation writes no domain
record, so the Command's transaction contains only the audit insert. Recording failed attempts too
is deliberate: content reached the provider either way, and the audit is the data-egress trail.

**Alternatives rejected**: no audit (no trail of data sent to a third party); `auditLogService.record`
directly as `prompt_actions` does (that module is not migrated; `cms` is); recording before the call
(would record requests refused for size or configuration, which sent nothing).

## R14 — Where the button is rendered

**Decision**: `PageBuilderHeaderActions` (shared chrome in `@endora-commerce/page-builder-admin`)
gains one generic, optional `extraActions?: ReactNode` rendered before Copy from language. `cms`'
`PageBuilderEditor` renders its own `PageBuilderTranslateAction` component into it. All strings are
in `cms`' bundle.

**Rationale**: the chrome is shared by `cms`, `invoices` and the e-mail builders and is translated in
the synthetic `core` scope; putting a `cms` feature's dialog, permission check and endpoint into it
would give the chrome module knowledge (`PageBuilderHeaderActions.tsx`'s own doc comment forbids
exactly that).

**Alternatives rejected**: add `onTranslate` props and dialog to the chrome (module knowledge in
shared chrome; keys in `_i18n`); a floating button outside Puck's header (inconsistent with Copy from
language, which the editor already knows).

## R15 — Which hosts show the action

**Decision (confirmed by the owner, 2026-10-17, spec Clarifications Q1)**: every host of `cms`'
`PageBuilderEditor` that tells it which language is edited. `PageBuilderEditor` gains nothing new for
this beyond `activeLanguage` (already a prop) and an optional `resource?: { type: string; id: string
| null }` used only for the audit entry. The three CMS editors already pass `languages` and
`activeLanguage`; the category zone passes `activeLanguage={language}`; the two blog editors pass
`languages`, `activeLanguage` and their resource. Without `activeLanguage` the action is not rendered.

The owner confirmed this answer; tasks T050–T051 stay in.

## R16 — Prompt

**Decision**: one fixed English system prompt in
`packages/modules/cms/src/backend/services/translation/prompt.ts`, naming the target language by its
code and English display name (`Intl.DisplayNames(['en'], { type: 'language' })`, ICU is in Node
22), and the source language when known; the rules of R6/R7; "translate for a web shop's public
content; do not add or omit content; return every id exactly once". The segments travel as a JSON
array in the user message. The prompt is covered by a snapshot test so that a change is reviewed.

**Alternatives rejected**: operator-editable instructions (spec A6, out of scope).

## R17 — Errors

**Decision**: error codes owned by `cms` (declared in `manifest.errorCodes`, sentences in `cms`'
bundle, en + pl):

| Code | HTTP | When |
| --- | --- | --- |
| `CMS_TRANSLATION_DISABLED` | 409 | the switch is off |
| `CMS_TRANSLATION_NOT_CONFIGURED` | 409 | no/dangling reference, incomplete credentials, unsupported provider |
| `CMS_TRANSLATION_UNAVAILABLE` | 409 | `credentials` module absent |
| `CMS_TRANSLATION_TOO_LARGE` | 413 | source text above `MAX_SOURCE_CHARACTERS` (`details.limit`, `details.characters`) |
| `CMS_TRANSLATION_PROVIDER_FAILED` | 502 | any chunk failed at the provider; `details.code` ∈ tokens `credentials_rejected` (401/403), `rate_limited` (429), `unavailable` (network, 5xx), `timeout`, `malformed` (every chunk unusable) |

A provider failure of **any** chunk fails the whole request (canvas unchanged, FR-024); an answer
that is usable for some segments and not others is a `200` with `untranslatedSegments > 0` (FR-020).
`LlmProviderError` from the library is mapped in one function with a table test.

## R18 — Data model and migrations

**Decision**: no new table, no new column, **no migration**. Settings rows come from the manifest
reconciler; audit rows go to the existing audit table. (`AGENTS.md` § Migrations is therefore not
exercised.)

## R19 — Test seam for the provider

**Decision**: `cms` registers `cmsTranslationLlmFetch: FetchLike | undefined` (default `undefined`),
which a test root overrides — the pattern `prompt_actions` uses (`promptActionsLlmFetch`). Contract
and integration tests never reach a real provider.

## R20 — Tenancy and channel scoping

**Decision**: nothing to scope. CMS entities are `@GlobalEntity()`; the endpoints read no
organisation data; the settings are platform-wide (null channel), as the existing Page Builder
settings effectively are. The Command Bus run requires the ambient admin TenantContext, which every
admin request has. Constitution XI and XII hold trivially; this is recorded so that a reviewer does
not have to re-derive it.

## R21 — OpenAI-compatible endpoints (owner decision 4, 2026-10-17)

**Decision**: implemented **once, in `@endora-commerce/llm-client`**, and used by both consumers.

- **Provider codes** become the credential's five: `anthropic`, `google`, `openai`, `deepseek`,
  `openai_compatible`. The list is declared once in `@endora-commerce/contracts`
  (`LlmProviderSchema`, `packages/contracts/src/prompt-actions.ts`, beside `LlmToolDefinition`);
  `PromptActionsProviderSchema` becomes an alias of it, `llm-client`'s `LlmProvider` is its type, and
  `credentials`' `llm` type is held to the same list by a unit test — one list, three readers, no
  drift.
- **Protocol**: `openai`, `deepseek` and `openai_compatible` all speak OpenAI chat completions through
  `OpenAiAdapter`; the adapter takes an optional `baseUrl` (the API root, the request goes to
  `<baseUrl>/chat/completions`, trailing slashes trimmed). Defaults: `openai` →
  `https://api.openai.com/v1` (byte-identical to today), `deepseek` → `https://api.deepseek.com`;
  `openai_compatible` has **no** default and `createLlmAdapter` refuses it without a Base URL. For
  the two non-OpenAI providers the token cap is sent as `max_tokens` (the field every compatible
  server accepts) instead of `max_completion_tokens`; `openai` keeps `max_completion_tokens`.
- **Anthropic and Google keep their public endpoints**; the owner's decision is about the OpenAI
  protocol, and a Base URL on those two is documented as not used. (Their wire formats have no
  third-party "compatible" ecosystem worth a switch here — YAGNI.)
- **Validation**: `createLlmAdapter` validates that a Base URL is an absolute `http:`/`https:` URL
  (`LlmConfigurationError` otherwise), so a consumer can turn a bad credential into
  `not_configured` instead of a failed call. `credentials` refuses the same at write time: its
  `FieldDefinition` gains an optional `format: 'url'` (additive; the frozen `kind` set is untouched,
  the core stays type-agnostic — it validates the *format*, not provider meaning), and the `llm`
  type's `baseUrl` declares it. The admin credential form renders a `format: 'url'` field as
  `<input type="url">`.
- **Credential type**: a new provider `openai_compatible` ("OpenAI-compatible (custom endpoint)")
  whose `baseUrl` is **required**; the other four keep it optional.
- **Consumers**: `prompt_actions`' factory and `cms`' capability both pass `baseUrl` to
  `createLlmAdapter` and catch only `LlmConfigurationError` → `not_configured`.

**Rationale**: the owner asked for exactly this; implementing it in the shared library is what the
library exists for (R2), and validating twice (write time for the operator, call time for old rows)
keeps a malformed URL from ever reaching `fetch`.

**Alternatives rejected**: a new credential *kind* for compatible endpoints (two places to choose an
LLM from; settings reference one `configurationType`); honouring Base URL on Anthropic/Google too
(no demand, more surface); a `url` member in the frozen `kind` set (changes a frozen enum every
consumer switches on).
